    2. 02
      Промпт со схемой

      Бэкенд собирает промпт: жёсткая JSON-схема, few-shot примеры и документация компонентов, которую реестр отдаёт сам.

      system + few-shot · JSON schema
    3. 03
      Ответ модели

      GigaChat MAX отвечает потоком и возвращает не код, а JSON: какие компоненты взять и с какими пропсами.

      streaming · выбор из реестра, не генерация кода
    4. 04
      Сборка ответа

      Фронт склеивает чанки и обновляет состояние раз в кадр, а не на каждый токен.

      requestAnimationFrame · батчинг
    5. 05
      Проверка схемой

      Ответ модели — граница: структура и типы проверяются в рантайме до рендера.

      zod safeParse · z.infer
    6. 06
      Если не сошлось

      Текст ошибки уходит обратно в модель вместе с промптом — обычно хватает одной попытки.

      retry with validation error
    7. 07
      Битая нода

      Деградация вместо падения: непрошедший узел заменяется плейсхолдером, остальные рендерятся.

      graceful degradation · error boundary
    8. 08
      Рендер

      По имени из реестра подставляется реальный компонент дизайн-системы — экран собран и работает.

      component registry · схема-билдеры для типовых экранов

    Как рассказываюПользователь описывает экран словами. Бэкенд собирает промпт с жёсткой JSON-схемой, few-shot примерами и документацией компонентов, которую реестр отдаёт сам. Модель отвечает потоком и возвращает не код, а выбор компонентов с пропсами. Фронт копит чанки и обновляет состояние раз в кадр, проверяет ответ схемой Zod, при ошибке шлёт её текст обратно в модель, а битый узел заменяет плейсхолдером — остальной экран остаётся живым. На последнем шаге имена из ответа превращаются в реальные компоненты дизайн-системы.

    Пилоты и метрики

    Ядро вакансии: PoC, A/B, выводы, доведение до прода. Здесь видно, есть ли процесс.

    2. Что значит «довести пилот до production-ready»: что обычно переписывается и сколько это занимает?

      Понимаю, чем буду занят половину времени — новыми прототипами или доведением старых.

    3. Инфраструктура A/B и feature flags уже есть или её предстоит строить? Какой сервис?

      Разница между «подключить SDK» и «написать всё самому» — месяцы работы.

    4. Кто считает метрики эксперимента и откуда я беру цифры: своя аналитика, внешний сервис, выгрузка?

      Если считать некому, «анализ метрик» из вакансии станет моей ручной работой.

    Главное, что нужно сказать

    • HTTP описывает формат общения. Он определяет, как выглядит запрос, как выглядит ответ и что означает каждая их часть.
    • HTTP сам ничего не помнит. Каждый запрос можно понять отдельно. Чтобы запомнить вход пользователя, сайт использует cookie, сессию или токен.
    • HTTPS — это HTTP плюс защита TLS. Содержание HTTP-запросов не меняется: TLS защищает способ, которым они передаются по сети.

    Механика обмена

    Как устроены запрос и ответ

    Запрос и ответ — это два сообщения. Ниже показан простой пример HTTP/1.1. У сообщения есть первая строка, заголовки с дополнительной информацией и иногда тело с основными данными.

    HTTP-запрос

    Клиент сообщает серверу, что нужно сделать и с какими данными.

    GET /api/users/42?full=true HTTP/1.1
Host: example.com
Accept: application/json
Authorization: Bearer <token>
    • GET — метод, то есть команда «получи данные».
    • /api/users/42 — путь, то есть адрес нужных данных на сервере.
    • ?full=true — параметр: дополнительное условие для запроса.
    • Заголовки — служебная информация. Например, нужный формат ответа и токен доступа.

    HTTP-ответ

    Сервер сообщает, что получилось, и при необходимости возвращает данные.

    HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=60

{ "id": 42, "name": "Ada" }
    • 200 OK — статус: запрос выполнен успешно.
    • Content-Type — заголовок, который говорит: тело ответа записано в формате JSON.
    • JSON — простой текстовый формат для передачи данных.
    • { "id": 42, ... } — тело, то есть сами данные ответа.

    Что уточнить на собеседовании

    HTTP называют stateless, то есть «без памяти»: сам протокол не помнит предыдущий запрос. Но сайт может помнить пользователя. Для этого он использует cookie — небольшую запись в браузере, сессию — данные на сервере, или токен — строку, которая подтверждает права пользователя.

    Защищённый канал

    Чем HTTPS отличается от HTTP

    Внутри HTTPS находится обычный HTTP: те же методы, статусы и заголовки. Разница в передаче данных. TLS создаёт защищённый канал — безопасный путь между клиентом и сервером.

    Важно

    HTTPS не означает, что сайт честный и в его коде нет ошибок. Он защищает данные только во время передачи между устройствами. Ниже разберём границы этой защиты.

    TLS простыми словами

    Что такое TLS и как он работает

    TLS расшифровывается как Transport Layer Security — «защита транспортного уровня». Это протокол, который создаёт защищённое соединение между двумя программами. В HTTPS такими программами обычно являются браузер и сервер. Это только название: TLS не доставляет данные по сети сам, а добавляет криптографическую защиту к их передаче.

    Самая простая формула: HTTPS = HTTP внутри TLS. Сначала клиент и сервер настраивают защиту, а уже потом передают HTTP-запросы и ответы.

    Три задачи TLS

    01

    Скрыть данные

    Это называется конфиденциальность. Данные шифруются, поэтому посторонний видит набор непонятных символов, а не пароль или текст запроса.

    02

    Заметить подмену

    Это называется целостность. Если данные изменят по дороге, проверка не пройдёт и получатель отклонит повреждённое сообщение.

    03

    Проверить сервер

    Это называется аутентификация. Браузер проверяет, что общается с владельцем нужного домена, а не с сервером злоумышленника.

    А как проверяется клиент?

    На обычном сайте TLS проверяет сертификат сервера, а пользователь входит по паролю или токену уже внутри защищённого HTTP. В mTLS, то есть взаимном TLS, сертификаты показывают обе стороны. Такой режим чаще используют между корпоративными сервисами.

    Важное слово

    Что такое сертификат

    TLS-сертификат — это электронное удостоверение сайта. Он связывает домен — имя сайта, например example.com, — с открытым ключом сервера. Сертификат можно показывать всем: секретов внутри него нет.

    Сертификат выдаёт центр сертификации, или CA. Это организация, которой доверяют браузер и операционная система. CA своей цифровой подписью подтверждает, что именно этот CA выдал сертификат для указанного домена.

    Цифровая подпись — это математическое доказательство. Оно позволяет проверить, кто подписал данные и не изменили ли их после подписи. Цепочка сертификатов — путь от сертификата сайта через один или несколько промежуточных CA к корневому CA, которому браузер уже доверяет.

    Браузер проверяет

    • домен в сертификате совпадает с адресом сайта;
    • срок действия сертификата ещё не закончился;
    • подписи в цепочке сертификатов верны;
    • цепочка приводит к доверенному корневому CA;
    • сертификат не был отозван, то есть досрочно отменён, если такая проверка доступна.

    Что сертификат не делает

    Сертификат сам не шифрует весь трафик и не доказывает, что сайт честный. Он помогает проверить домен и открытый ключ. Шифрование выполняет TLS с помощью временных ключей соединения.

    SSL и TLS — это одно?

    SSL — старый предшественник TLS. Старые версии SSL больше не считаются безопасными. Фразу «SSL-сертификат» до сих пор используют по привычке, но современные сайты работают с TLS.

    Как начинается защищённое соединение

    Начальная настройка TLS называется handshake, по-русски — «рукопожатие». Ниже упрощённый, но технически точный порядок для TLS 1.3.

    1. Клиент говорит, что умеет

      Браузер отправляет ClientHello: поддерживаемые версии TLS, варианты шифрования, случайные данные и временный открытый ключ.

    2. Сервер выбирает настройки

      Сервер отвечает ServerHello: выбирает версию и алгоритмы, то есть математические способы защиты, а также отправляет свой временный открытый ключ.

    3. Обе стороны получают общий секрет

      Клиент и сервер независимо вычисляют одинаковый общий секрет — секретное число, известное только им. Оно по сети не отправляется. Перехватить только открытые данные недостаточно, чтобы его восстановить.

    4. Сервер доказывает свою личность

      Он отправляет цепочку сертификатов и цифровую подпись. Подпись доказывает, что у сервера есть закрытый ключ от сертификата, хотя сам ключ не передаётся.

    5. Браузер проверяет доказательства

      Он проверяет домен, срок, цепочку доверия и подпись сервера. При серьёзной ошибке браузер предупреждает пользователя или разрывает соединение.

    6. Стороны проверяют всё рукопожатие

      Сообщения Finished подтверждают, что обе стороны получили один секрет и что никто не изменил переговоры по дороге.

    7. Начинается передача HTTP

      Из общего секрета создаются временные сеансовые ключи. Ими TLS шифрует и проверяет HTTP-запросы и ответы до конца соединения.

    Почему ключ временный

    В TLS 1.3 для каждого нового соединения создаются временные ключи. Поэтому кража постоянного закрытого ключа сервера обычно не позволяет расшифровать старые записанные соединения. Это свойство называют forward secrecy: оно защищает старые сеансы — украденный позже ключ сервера обычно не раскрывает уже записанный трафик.

    Какие ключи здесь используются

    Ключ Кто его видит Зачем он нужен
    Открытый ключ сертификата Можно показывать всем Помогает проверить цифровую подпись сервера.
    Закрытый ключ сервера Только сервер Позволяет серверу создать подпись и доказать, что сертификат его.
    Временные ключи обмена У каждой стороны своя секретная часть Позволяют вычислить общий секрет, не отправляя его по сети.
    Сеансовые ключи Только клиент и сервер Быстро шифруют и проверяют данные текущего соединения.
    Чуть глубже Как TLS защищает каждое сообщение
    1. TLS делит поток данных на небольшие части — записи.
    2. Алгоритм шифрует содержимое записи сеансовым ключом.
    3. К записи добавляется проверочный код — короткая математическая проверка, которая показывает, меняли данные или нет.
    4. Получатель проверяет код и только потом принимает данные.

    Современные алгоритмы, например AES-GCM и ChaCha20-Poly1305, одновременно шифруют данные и проверяют их целостность. Такой способ называют аутентифицированным шифрованием.

    Что именно защищает HTTPS

    TLS защищает

    • путь страницы и параметры после домена;
    • заголовки, cookie, токены и пароли;
    • тело запроса и тело ответа;
    • данные от чтения и незаметной подмены в пути;
    • проверку сервера, если сертификат успешно проверен.

    TLS не защищает

    • данные до отправки и после получения;
    • устройство, если на нём есть вредоносная программа;
    • базу данных, логи и ошибки в коде сервера;
    • от фишингового сайта с собственным правильным сертификатом;
    • IP-адрес, время соединения и примерный объём трафика;
    • домен часто виден через DNS — систему поиска IP-адреса сайта — и служебные данные TLS.

    TLS — не всегда сквозное шифрование

    TLS защищает путь только до точки, где соединение заканчивается. Это может быть сам сервер, CDN — промежуточная сеть доставки данных, — или балансировщик нагрузки — программа, распределяющая запросы между серверами. В этой точке данные расшифровываются. Поэтому HTTPS не равно сквозному шифрованию между двумя пользователями.

    Готовый ответ на собеседовании

    «TLS — это протокол защиты соединения. Он шифрует данные, обнаруживает подмену и с помощью сертификата проверяет сервер. Во время handshake клиент и сервер согласуют алгоритмы, браузер проверяет сертификат сервера, а обе стороны получают общий секрет. Из него создают временные сеансовые ключи. После этого HTTP передаётся в зашифрованном виде. TLS защищает данные в пути, но не исправляет уязвимости сайта и не делает сам сайт честным».

    Техническая основа: TLS 1.3 — RFC 8446, HTTP Semantics — RFC 9110 и сертификаты X.509 — RFC 5280.

    Команды запроса

    HTTP-методы: что хочет сделать клиент

    4xx · запрос не выполнен

    Запрос, доступ или состояние

    4xx описывает результат запроса, а не назначает виновного.

    400Bad Request

    Запрос неправильно сформирован. Например, JSON сломан.

    401Unauthorized

    Нет подходящих данных для подтверждения личности: токена нет или он неверный.

    403Forbidden

    Сервер понял запрос, но отказывается его выполнять. Часто не хватает прав.

    404Not Found

    Ресурс не найден. Иногда сервер так скрывает существование закрытого ресурса.

    409Conflict

    Запрос конфликтует с текущим состоянием: версия устарела или имя занято.

    422Unprocessable Content

    Формат понятен, но данные нельзя применить: например, email некорректен.

    Заголовки и кеш: что браузеру делать с ответом

    Короткий ответ. HTTP-заголовки — строки вида имя: значение. Они объясняют, что отправлено, кто делает запрос и можно ли сохранить ответ. Сами данные обычно находятся в теле сообщения.

    Формат данных

    Content-Type ↔ Accept

    Content-Type — что отправлено. Accept — что клиент хочет получить.

    «Отправляю JSON» ↔ «Хочу JSON»

    Память браузера

    Set-Cookie ↔ Cookie

    Set-Cookie просит браузер сохранить cookie. Cookie отправляет его обратно.

    Сервер → браузер ↔ браузер → сервер

    Проверка по версии

    ETag ↔ If-None-Match

    ETag помечает версию ответа. Клиент спрашивает: «Версия всё ещё такая?»

    ETag: "v1" ↔ If-None-Match: "v1"

    Проверка по времени

    Last-Modified ↔ If-Modified-Since

    Last-Modified сообщает дату изменения. Клиент спрашивает: «После этой даты менялось?»

    Похожая задача, но проверка идёт по времени

    Кеш без магии

    Кеш — это сохранённая копия готового ответа

    Он экономит время и трафик. Главное — понять, свежая копия или уже устарела.

    Cache-Control

    Три правила, которые нельзя путать

    max-age=60 Если сохранил — 60 секунд не проверяй

    Пока копия свежая, браузер обычно не обращается к серверу.

    no-cache Сохрани, но сначала проверь

    Хранить можно. Перед повторным использованием нужна проверка сервера.

    no-store Не сохраняй

    Ответ не должен попадать в кеш. Следующий запрос получает его заново.

    Главная ловушка: no-cache не означает «не хранить». Для запрета хранения нужен no-store.

    DNS / Anycast

    Как выбирается Edge

    Провайдер может направлять запрос через DNS, Anycast или их сочетание. Выбор учитывает маршрут, доступность и нагрузку.

    Дополнительный Shield-кеш уменьшает число одинаковых запросов от разных Edge к Origin.

    versioned URL / purge

    Как обновлять контент

    Надёжнее менять имя файла при новой версии. Purge полезен для срочного обновления, но не очищает кеш браузера.

    stale-while-revalidate

    Как скрыть ожидание

    CDN может временно отдать старую копию, если это разрешено. Но s-maxage включает proxy-revalidate: общий кеш не должен отдавать stale без успешной проверки.

    Age / Cache-Status

    Как понять возраст копии

    Age показывает возраст, а не остаток TTL. Cache-Status стандартизирует диагностику; заголовки провайдеров отличаются.

    Origin unavailable

    Что будет при сбое

    Свежая копия обычно продолжит работать. Старую можно отдать только если это разрешают правила кеша и CDN.

    cache poisoning / deception

    Как общий кеш становится опасным

    Неучтённый в Cache Key ввод или маскировка персональной страницы под файл могут сохранить неправильный ответ для других.

    request collapsing

    Как не перегрузить Origin

    CDN может объединить одинаковые одновременные MISS в один запрос, чтобы не устроить «стадо» обращений к Origin.

    CDN не заменяет Origin

    При сквозном MISS на всех уровнях кеша и для некешируемых запросов Origin всё равно выполняет работу.

    CDN не гарантирует безопасность

    Ошибочный Cache Key, открытый Origin или неверные TLS-настройки остаются проблемой.

    6. object-src 'none', base-uri 'none' — закрывают плагины и подмену базового URL

    Понять за минуту

    Три версии — три способа везти файлы

    Браузеру нужны три файла. Разница версий — в том, сколько соединений и кто ждёт, когда один пакет потерялся.

    ▤ Страница HTML
    ◆ Оформление CSS
    ▧ Картинка фото товара
    1. HTTP/1.1 — текстовый; несколько соединений, по одному файлу на каждом; потерялся пакет картинки → ждёт только её соединение
    2. HTTP/2 — бинарные кадры, в браузере только с TLS; одно соединение, всё вперемешку; потерялся пакет → ждут все три файла
    3. HTTP/3 — бинарные кадры, TLS 1.3 внутри QUIC; одно соединение, у каждого файла свой поток; потерялся пакет → ждёт только поток картинки

    Как сказатьHTTP/1.1 везёт один файл за раз, поэтому браузер открывает несколько соединений. HTTP/2 возит всё по одному соединению вперемешку, но потерянный пакет тормозит всех. HTTP/3 делает то же поверх QUIC на UDP: потоки независимы, потеря тормозит только свой поток, соединение стартует быстрее и переживает смену сети. HTTP/1.1 текстовый, 2 и 3 — бинарные и в браузере всегда с TLS.

    Самый важный новый термин

    Что значит «QUIC поверх UDP»

    UDP — это простой способ отправить отдельную датаграмму. Он сам не устанавливает надёжное соединение, не выстраивает данные по порядку и не повторяет потерянное.

    QUIC использует UDP как конверт, но строит внутри полноценный транспорт: добавляет подтверждения, восстановление потерянных данных, контроль перегрузки, независимые потоки и обязательное шифрование через TLS 1.3. Поэтому QUIC создаёт настоящее соединение, хотя UDP под ним соединения не создаёт.

    ✉

    Пример на пальцах. UDP — обычный конверт без отслеживания. QUIC печатает номера заказов, просит подтверждение, повторно отправляет потерянные данные, запечатывает содержимое и раскладывает разные заказы по отдельным папкам.

    ACKНадёжность

    Получатель подтверждает, какие данные пришли.

    LOSSВосстановление потерь

    QUIC повторно передаёт потерянные данные в новых пакетах.

    TLS 1.3Шифрование встроено

    Защита создаётся вместе с QUIC-соединением, а не отдельным слоем после TCP.

    STREAMSНезависимые потоки

    Потеря в одном stream не блокирует доставку данных в другом.

    CONGESTIONНе перегружать сеть

    QUIC регулирует скорость всей связи, когда сеть занята.

    CONNECTION IDПережить смену сети

    Соединение может продолжиться после изменения IP и порта, когда новый путь проверен.

    Почему именно UDP? QUIC можно развивать в приложениях быстрее, не меняя TCP в операционных системах и сетевом оборудовании.

    Если UDP заблокирован? Клиент обычно может вернуться к HTTP/2 по TCP. Поэтому наличие HTTP/3 не гарантирует, что каждый запрос пойдёт по нему.

    Как браузер выбирает версию? Для HTTPS протокол h2 выбирают через ALPN во время TLS. Через Alt-Svc сервер может подсказать адрес с поддержкой HTTP/3. Браузер пробует QUIC, а внутри его TLS-handshake стороны выбирают h3 через ALPN. Если QUIC не работает, браузер возвращается к TCP. Версия выбирается для каждого участка отдельно: браузер может говорить с CDN по h3, а CDN с origin — по h2.

    Как быстро начинается связь? Новое QUIC-соединение обычно защищается за один сетевой круг, а повторное иногда использует 0‑RTT. Сервер может отклонить ранние данные, а действия с риском повтора нельзя бездумно отправлять через 0‑RTT.

    На пальцах: одна длинная пронумерованная лента. Если кусок потерялся, следующие куски нельзя отдать приложению раньше него.

    На собеседовании: QUIC использует UDP как основу и сам добавляет нужные гарантии.
    QUICЗащищённый транспорт поверх UDP

    На пальцах: умная служба доставки внутри простых UDP-конвертов.

    На собеседовании: даёт HTTP/3 TLS 1.3, streams, loss recovery и connection migration.

    На пальцах: кадр CSS, затем кадр JS, затем снова CSS — получатель собирает каждый поток по его номеру.

    На собеседовании: HTTP/2 убрал прикладную очередь HTTP/1.1.

    На собеседовании: кадры проще смешивать по потокам и однозначно разбирать.

    На собеседовании: HPACK — для HTTP/2; QPACK адаптирован к независимым QUIC-stream в HTTP/3. Если нужная запись dynamic table ещё не пришла, декодирование всего блока заголовков запроса подождёт; ждать могут несколько streams.

    На пальцах: в кассе завис первый покупатель — очередь стоит. В TCP потерянный байт задерживает выдачу следующих.

    На собеседовании: HTTP/3 убирает транспортную TCP-блокировку между независимыми streams. Но порядок внутри одного stream, зависимости приложения и ожидание данных QPACK остаются.

    Четыре частые ошибки

    МИФ«HTTP/1.1 грузит весь сайт строго по одному файлу»

    Браузеры открывают несколько TCP-соединений. Очередь относится к конкретному соединению, а не ко всему интернету.

    МИФ«В HTTP/2 блокировок больше нет»

    Прикладную очередь убрали, но все streams делят один упорядоченный TCP-поток.

    МИФ«HTTP/3 ненадёжен, ведь UDP ничего не гарантирует»

    Гарантии реализует QUIC: подтверждения, восстановление потерь, порядок внутри stream и контроль перегрузки.

    МИФ«HTTP/3 всегда самый быстрый»

    На хорошей сети разница может быть небольшой. Результат зависит от задержки, потерь, сервера, CDN, кеша и размера ресурсов.

    Готовый развёрнутый ответ

    «Семантика HTTP в версиях не меняется: остаются те же методы, URL, заголовки и коды ответа. HTTP/1.1 передаёт начальную строку и заголовки как текст поверх TCP; тело ответа при этом может быть бинарным. Для параллельной загрузки браузеры обычно открывают несколько соединений. HTTP/2 вводит бинарные кадры, multiplexing и HPACK, поэтому много запросов могут идти потоками внутри одного TCP-соединения. Но потеря TCP-пакета может задержать все эти потоки. HTTP/3 переносит HTTP на QUIC поверх UDP. QUIC интегрирует TLS 1.3, даёт независимые streams, восстановление потерь и connection migration. Поэтому потеря в одном stream не обязана блокировать другие, а соединение лучше переживает мобильную сеть. При этом HTTP/3 не гарантирует ускорение в любой ситуации».

    Техническая основа: RFC 9112 — HTTP/1.1, RFC 9113 — HTTP/2, RFC 9114 — HTTP/3, RFC 9000 — QUIC и RFC 9204 — QPACK.

    Лексическое окружение
    Объект, в котором движок хранит переменные конкретного вызова, плюс ссылка на внешнее окружение.

    Раздел 02.7 / JavaScript

    this: кто вызывает, тот и this

    Четыре вопроса — четыре коротких ответа. Сцена показывает, строка «Как сказать» — то, что говоришь.

    00

    Чему равен this?

    Зависит от того, как функция вызвана, а не где написана. Четыре случая: через точку, просто вызов, явно через call/apply/bind, через new.

    Как сказатьthis зависит от вызова, а не от места объявления: через точку — объект перед точкой, просто вызов — undefined в strict, call/apply/bind — что передали, new — новый объект.

    01

    Почему this «теряется» и как вернуть?

    Метод, переданный как колбэк, вызывается без объекта. Лечение: bind, стрелочная обёртка или стрелка в поле класса.

    Как сказатьКонтекст теряется, когда метод передают как колбэк — его вызывают без точки. Лечу bind, стрелочной обёрткой или стрелкой в поле класса.

    02

    Что со this у стрелочных функций?

    Своего this нет: берётся из места объявления. Хороши внутри методов и колбэков, плохи как методы объекта.

    Как сказатьСтрелочная функция своего this не имеет и берёт его из места объявления, как замыкание. Поэтому она хороша внутри методов и колбэков и плоха как метод объекта; call и bind на неё не действуют.

    03

    this в классах и React

    Методы класса лежат на прототипе и теряют this в onClick; стрелка в поле класса чинит. В функциональных компонентах this не нужен.

    Как сказатьВ классах методы на прототипе, и при передаче в onClick this теряется; лечится стрелкой в поле класса или bind. В функциональных компонентах this не нужен — работает замыкание.

    Как определить this

    1. через точку — объект перед точкой
    2. просто вызов — undefined в strict, window в sloppy
    3. new — новый объект
    4. call / apply / bind — то, что передали; bind — навсегда
    5. стрелка — своего this нет, берёт снаружи; call и bind не действуют
    6. обработчик DOM — обычная функция — элемент; стрелка — снаружи

    Ответ за 20 секунд — три фразы

    this зависит от того, как функция вызвана, а не где написана: через точку — объект перед точкой, без объекта — undefined в strict, через new — новый объект, через call, apply, bind — то, что передали. Стрелочная функция своего this не имеет и берёт его из места объявления. Контекст теряется, когда метод передают как колбэк, — лечится bind или стрелкой.

    Раздел 02.8 / JavaScript

    Прототипы: откуда у объекта методы

    Четыре вопроса — четыре коротких ответа. Сцена показывает, строка «Как сказать» — то, что говоришь.

    00

    __proto__ и prototype: в чём разница?

    __proto__ — ссылка объекта на прототип, своя у каждого объекта. prototype — объект-родитель у функции-конструктора: что положили туда, видят все экземпляры.

    Как сказать__proto__ — ссылка объекта на его прототип, меняется только у этого объекта. prototype — свойство конструктора, объект-родитель для всех экземпляров: изменение в нём видят все, кто на него ссылается.

    01

    Откуда у объекта методы, которых в нём нет?

    У объекта есть скрытая ссылка на прототип. Чтение свойства идёт по цепочке до Object.prototype и null.

    Как сказатьУ каждого объекта есть скрытая ссылка [[Prototype]]; при чтении свойства движок идёт по цепочке до Object.prototype и null. Методы лежат в прототипе один раз, данные у каждого объекта свои.

    02

    Как задаётся связь с прототипом?

    Object.create, оператор new с функцией-конструктором или class — это сахар над тем же. prototype — свойство функции, [[Prototype]] — ссылка у объекта.

    Как сказатьСвязь задаётся Object.create, оператором new, который связывает новый объект с F.prototype, или class — это сахар над тем же механизмом. prototype — свойство функции, [[Prototype]] — ссылка у объекта.

    03

    Методы общие, данные свои

    Метод в прототипе один на всех. Запись создаёт собственное свойство и перекрывает прототипное; in идёт по цепочке, hasOwnProperty — нет.

    Как сказатьМетоды лежат в прототипе один раз, данные у каждого объекта свои. Запись создаёт собственное свойство и перекрывает прототипное; in идёт по цепочке, hasOwnProperty смотрит только своё.

    04

    Как работают extends, super и instanceof?

    extends выстраивает цепочку прототипов, super вызывает конструктор родителя, instanceof ищет prototype в цепочке.

    Как сказатьextends выстраивает цепочку прототипов, super вызывает конструктор родителя для того же this, instanceof проверяет наличие prototype в цепочке. Массивы и функции устроены так же.

    Шесть фактов

    1. [[Prototype]] — скрытая ссылка объекта; читать через Object.getPrototypeOf
    2. prototype — свойство функции-конструктора; туда попадают методы
    3. new — создать {}, связать с F.prototype, вызвать с this, вернуть
    4. class — сахар над функцией и prototype; extends строит цепочку
    5. запись — создаёт своё свойство, прототип не меняется
    6. instanceof — есть ли F.prototype в цепочке объекта

    Ответ за 20 секунд — три фразы

    У каждого объекта есть скрытая ссылка на прототип; при чтении свойства движок идёт по цепочке до Object.prototype и null. Функции-конструкторы и class кладут методы в prototype один раз, а new связывает новый объект с ним. Запись создаёт своё свойство и не трогает прототип, instanceof проверяет, есть ли prototype в цепочке.

Снизу вверх собираются DOM-узлы, и только commit применяет флаги к документу; кадр и эффекты идут после.

    01

    Что за чем идёт — и почему?

    Слева — порядок моментов по трём этапам, справа — карточка текущего момента: что появилось и откуда оно взялось. Реконсиляция — не отдельный шаг после построения дерева, а действие внутри каждого beginWork.

    Как сказатьСначала React создаёт корень fiber и кладёт в его очередь один элемент — рендер это задача планировщика, её можно прервать. Затем render phase: с корня вниз, на каждом узле вызов компонента и сразу реконсиляция его детей — элементы рождаются только при вызове, поэтому дерево строится по одному уровню. Когда дети готовы, снизу вверх создаются DOM-узлы в памяти. И только потом commit — одним движением, чтобы пользователь не увидел половину дерева.

    02

    Что такое Virtual DOM?

    Дерево обычных объектов-описаний, которое React строит заново на каждом рендере и по которому обновляет настоящий DOM.

    Как сказатьVirtual DOM — это дерево лёгких объектов-описаний, которое компонент возвращает на каждом рендере. На первом рендере React строит по нему настоящий DOM и вставляет целиком одним коммитом. Это не ускоритель — это способ описать результат и отдать React вычисление правок.

    03

    Что такое Fiber?

    Внутренний узел React на каждый элемент: хранит стейт как список хуков и связи с соседями, чтобы обход дерева можно было прерывать и возобновлять.

    Как сказатьFiber — внутренний узел React на каждый элемент: хранит тип, пропсы, стейт и ссылки на ребёнка, соседа и родителя, поэтому обход можно прервать и продолжить. Стейт лежит на fiber как список хуков: он создаётся при первом вызове компонента в порядке вызовов, а при обновлении React идёт по нему по позиции — поэтому хуки нельзя вызывать условно. React держит два дерева и после обновления переключает указатель.

    04

    Откуда берутся хуки

    Шаг 05 крупным планом: вызов идёт из твоего кода в пакет react, оттуда в диспетчер, а тот пишет слот в карточку, которая рендерится сейчас.

    Как сказатьХук ничего не получает сверху: он обращается к диспетчеру, а тот знает, какая карточка рендерится сейчас, и занимает в ней слот. Слоты нумеруются по порядку вызова — поэтому хук нельзя ставить под if, в цикл или после return.

    05

    Один цикл по шагам: откуда берутся хуки и где реконсиляция

    Движок React идёт по карточкам (fiber) и вызывает твою функцию, держа её карточку «в руках»: каждый хук пишет слот в эту карточку. Возвращённое описание (Virtual DOM) движок сравнивает с детьми карточки — это реконсиляция. Потом пометки уходят в DOM одним куском — это commit.

    Как сказатьДвижок React вызывает компонент, держа его карточку — fiber. Каждый useState и useEffect внутри через диспетчер пишет слот в эту карточку, так хуки получают память. То, что вернул компонент, — описание, Virtual DOM. Движок сравнивает его с детьми карточки — это реконсиляция — и ставит пометки. Commit переносит пометки в DOM одним куском, а после отрисовки запускаются эффекты. Клик кладёт обновление в слот и запускает круг заново.

    06

    Что происходит при setState?

    Две фазы: render — построить новое дерево и найти разницу, commit — применить её к DOM.

    Как сказатьОбновление идёт в две фазы. Render — чистая и прерываемая: вызываются компоненты, строится новое дерево, считается разница. Commit — синхронная, из трёх подфаз: снимок до правок, мутации DOM, layout. useLayoutEffect — до отрисовки, useEffect — после. И ререндер не равен обновлению DOM: нет разницы — DOM не трогается.

    07

    Как работает реконсиляция?

    Сопоставление нового дерева со старым: что переиспользовать, что пропатчить, что создать или удалить — и только это уходит в DOM.

    Как сказатьРеконсиляция сопоставляет новый элемент со старым fiber: разный тип — поддерево пересоздаётся, тот же тип — узел переиспользуется и обновляются только пропсы, дети списка ищутся по key. На выходе — флаги на узлах, а в DOM уходит только разница.

    08

    Что делает key при сравнении

    Реконсиляция ищет прошлую карточку по key. По индексу ключи всегда совпадают по позиции, поэтому состояние достаётся соседу.

    Как сказатьВнутри одного уровня React ищет прошлую карточку по type и key. С key={index} после вставки в начало ключи совпадают по позиции: карточка нулевой строки достаётся новому элементу вместе с её состоянием, фокусом и незакоммиченным вводом. С устойчивым key из данных карточки находятся по ключу и переезжают вместе с состоянием, а создаётся только одна новая.

    09

    Зачем нужен key?

    Стабильный идентификатор элемента списка, по которому React узнаёт его между рендерами вместо сравнения по позиции.

    key={i}по позиции

      key={todo.id}по личности

        новый ключ не нашёлся — создан новый узел; остальные узнаны по ключу и переехали вместе с галочкой

        Как сказатьБез key React сравнивает детей по позиции: при вставке в начало он считает, что все элементы просто изменились, и состояние остаётся на позициях. Со стабильным key он узнаёт элемент и переносит состояние вместе с ним. Индекс годится только для списков, которые не меняют порядок.

        свой setState или родитель перерендерился или изменился context или внешний стор → компонент вызывается заново

        Рассказ на минуту — из пяти фраз

        Virtual DOM — это дерево лёгких объектов-описаний, которое компонент возвращает на каждом рендере; на первом рендере React строит по нему DOM и вставляет одним коммитом. Fiber — внутренний узел на каждый элемент со стейтом и ссылками на соседей, поэтому обход можно прерывать; React держит два дерева и после обновления переключает указатель. Поэтому индекс в key ломает состояние списка, а ререндер не равен обновлению DOM.

        Раздел 03.2 / React

        Ререндер: почему, сколько стоит и как остановить

        Пять сцен — пять вопросов про ререндер, которые задают сениору. Под каждой — фраза, которую произносишь.

        00

        Что такое ререндер и сколько он стоит?

        Ререндер — это вызов функции компонента и сравнение результата с детьми его карточки. Дети по умолчанию вызываются вместе с родителем. DOM меняется только там, где сравнение нашло разницу.

        Как сказатьРерендер — это не обновление DOM, а вызов функции и сравнение результата: дети вызываются вместе с родителем, а в DOM уходит только найденная разница. Поэтому оптимизируют не «ререндеры вообще», а лишние вызовы там, где они дорогие, и начинают с Profiler.

        01

        Как работает React.memo и почему он «не работает»?

        memo просит движок сравнить новые пропсы со старыми по ссылке и пропустить вызов, если всё совпало. Новая стрелка или объект прямо в JSX ломают сравнение — лечатся useCallback и useMemo.

        Как сказатьmemo сравнивает пропсы по ссылке через Object.is и пропускает вызов, если всё совпало. Стрелка или объект, созданные в JSX, каждый раз новые — memo перестаёт работать, поэтому их держат стабильными через useCallback и useMemo. Сама проверка не бесплатна: memo ставят на дорогие поддеревья, а React Compiler делает это автоматически.

        02

        Как убрать лишний ререндер без memo?

        Опусти state туда, где он нужен: родитель не вызван — дети не пересоздаются. Подними тяжёлый контент выше через children: тот же объект элемента движок пропускает сам.

        Как сказатьСначала структура, потом memo: опускаю state в тот компонент, которому он нужен, и тогда родитель с тяжёлыми детьми не вызывается вовсе. Если state нужен обёртке, тяжёлый контент передаю через children — элемент создан выше, ссылка та же, и React пропускает его без memo.

        03

        Почему контекст ререндерит всех и что с этим делать?

        Изменение value будит всех подписчиков useContext, минуя memo. Держи value стабильным через useMemo, дели контексты по смыслу, а для сторов подписывайся на срез через селектор.

        Как сказатьСмена value у Provider вызывает всех подписчиков контекста, и memo их не защищает. Поэтому value оборачиваю в useMemo, режу контексты по смыслу — тема отдельно от пользователя, а для внешних сторов беру useSyncExternalStore с селектором, чтобы компонент просыпался только на свой срез.

        04

        Что делают startTransition и useDeferredValue?

        Они не ускоряют рендер, а понижают его приоритет: срочное обновление проходит сразу, тяжёлое строится по кусочкам между кадрами и может быть прервано новым вводом.

        Как сказатьТранзишн не ускоряет работу — меняет приоритет. Ввод в поле идёт срочно, тяжёлый список помечен как транзишн и строится по кусочкам между кадрами; новый ввод выбрасывает недостроенный черновик, а экран показывает старый список с isPending. useDeferredValue делает то же самое для значения без отдельного setState.

        Семь ловушек, которые ищут на собеседовании

        1. key={index} в списке, который сортируют или режут из середины → состояние и фокус уезжают к чужому элементу.
        2. Компонент, объявленный внутри другого компонента → каждый рендер новый тип → размонтирование, потеря state и фокуса.
        3. style={{…}}, items.filter(…) или стрелка прямо в JSX → новая ссылка → memo у ребёнка не срабатывает.
        4. setState в useEffect без условия или с объектом в зависимостях → бесконечный цикл ререндеров.
        5. value={{…}} у Provider без useMemo → все подписчики просыпаются на каждый рендер родителя.
        6. memo и useMemo на всём подряд → сравнения и память дороже самого рендера; сначала Profiler, потом точечно.
        7. Производное значение через useEffect + setState → лишний рендер; считать во время рендера или в useMemo.

        Рассказ на минуту — из шести фраз

        Ререндер — это вызов функции компонента и сравнение результата со старым деревом; DOM трогается только там, где нашлась разница. Его запускают свой setState, ререндер родителя, контекст и внешний стор, а дети по умолчанию вызываются вместе с родителем. Останавливать лучше структурой: опустить state вниз, поднять тяжёлый контент вверх через children; потом memo, но он работает только со стабильными пропсами, поэтому useCallback и useMemo. Контекст обходит memo: value через useMemo, узкие контексты, для сторов — селекторы через useSyncExternalStore. Для тяжёлых обновлений — startTransition и useDeferredValue: срочное сразу, тяжёлое по кусочкам, и его можно прервать. Оптимизация начинается с Profiler, а не с memo везде; React Compiler расставляет мемоизацию сам.

        Раздел 03.3 / React

        memo, useCallback и useMemo

        Три инструмента — одна идея: сравнить по ссылке и переиспользовать прошлый результат. По сцене на каждый: проблема, лечение, цена.

        00

        memo — пропустить вызов компонента

        Проблема: родитель перерендерился, ребёнок с теми же пропсами вызывается зря. Решение: memo сравнивает пропсы по ссылке и при совпадении пропускает вызов.

        Как сказатьmemo решает одну проблему: ребёнок вызывается зря при каждом рендере родителя. Он сравнивает пропсы по ссылке через Object.is и при совпадении пропускает вызов, оставляя старый результат. Цена — сравнение на каждый рендер, поэтому ставлю его на дорогие поддеревья со стабильными пропсами, а не везде.

        01

        useCallback — та же функция между рендерами

        Проблема: функция, объявленная в теле компонента, каждый рендер новая — ломает memo у детей и deps у эффектов. Решение: useCallback возвращает прошлую ссылку, пока deps те же.

        Как сказатьuseCallback нужен, когда ссылку на функцию кто-то сравнивает: memo-ребёнок, deps эффекта, подписка. Он кладёт функцию в слот хука с deps и возвращает ту же ссылку, пока deps не изменились. Саму функцию он не ускоряет и замыкание всё равно создаётся, так что без потребителя это лишний расход.

        02

        useMemo — значение из слота, пока deps те же

        Две проблемы: дорогое вычисление повторяется на каждый рендер, а объект, созданный в рендере, каждый раз новый. Решение: useMemo хранит результат и отдаёт его, пока deps не изменились.

        Как сказатьuseMemo хранит результат фабрики вместе с deps и пересчитывает только при их смене. Закрывает две вещи: тяжёлое вычисление, которое иначе повторяется при любом рендере, и стабильную ссылку на объект для memo-детей и deps. Это подсказка, а не гарантия, и не для дешёвых вычислений: сначала Profiler, а React Compiler делает это автоматически.

        Коротко и по фактам

        memo(Component)

        Решаетребёнок вызывается зря при рендере родителя

        Ценасравнение пропсов на каждый рендер родителя

        Не надодешёвый компонент; пропсы всё равно новые

        useCallback(fn, deps)

        Решаетновая ссылка функции ломает memo детей и deps эффектов

        Ценасравнение deps; замыкание создаётся всё равно

        Не надоссылку никто не сравнивает

        useMemo(factory, deps)

        Решаетдорогое вычисление и новый объект на каждый рендер

        Ценасравнение deps и память под кеш; кеш без гарантии

        Не надодешёвое вычисление

        Все три сравнивают через Object.is, все три стоят времени и памяти. Порядок действий: Profiler → структура (state вниз, контент вверх) → точечная мемоизация. React Compiler расставляет её автоматически.

        Рассказ на полминуты — из четырёх фраз

        memo пропускает вызов компонента, если пропсы те же по ссылке, — лечит лишние ререндеры детей. useCallback и useMemo держат стабильную ссылку на функцию и значение, пока не изменились deps, — без них memo не работает, а эффекты перезапускаются зря; useMemo ещё и кеширует дорогие вычисления. Все три сравнивают через Object.is и сами стоят времени, поэтому ставятся по Profiler на горячие места, а не везде. React Compiler делает эту мемоизацию автоматически.

        Раздел 03.4 / React

        Хуки: useEffect, useRef и ловушки

        Пять сцен — пять вопросов, на которых сыпятся: когда срабатывает эффект, почему счётчик застрял, откуда чужие данные, зачем ref и как устроены свои хуки.

        00

        Когда срабатывает useEffect, а когда useLayoutEffect?

        Оба запускаются после того, как правки попали в DOM. useLayoutEffect — синхронно, до кадра: для измерений и позиционирования. useEffect — после кадра, отдельной задачей: для запросов, подписок, аналитики.

        Как сказатьОба эффекта идут после commit, разница — по какую сторону кадра. useLayoutEffect синхронный и блокирует отрисовку, поэтому в нём измеряют и двигают DOM, чтобы не было мигания. useEffect запускается после кадра отдельной задачей — туда идут запросы, подписки и аналитика. По умолчанию useEffect.

        01

        Почему счётчик застрял на единице? Stale closure

        Эффект с пустыми deps один раз замкнул count = 0, и таймер вечно считает 0 + 1. Лечится функциональным обновлением, честными deps или ref с последним значением.

        Как сказатьФункция внутри таймера замкнула count из первого рендера, а эффект с пустыми deps больше не пересоздавался — таймер вечно считает ноль плюс один. Лечу функциональным обновлением setCount(c => c + 1), потому что React сам передаёт актуальное значение; альтернативы — честные deps или ref с последним значением. Линтер exhaustive-deps такие места подсвечивает.

        02

        Откуда чужие данные? Гонка запросов и cleanup

        Ответы приходят не по порядку: поздний ответ старого id перезаписывает свежие данные. Cleanup эффекта помечает старый запрос устаревшим или отменяет его через AbortController.

        Как сказатьЭто гонка: запрос для старого id ответил позже нового и перезаписал данные. Промис отменить нельзя, но можно проигнорировать: в cleanup эффекта ставлю флаг ignore, и поздний ответ не попадает в state. Следующий уровень — AbortController, который отменяет сам запрос; React Query делает это по ключу автоматически.

        03

        Зачем useRef, если есть useState?

        state — значение, которое видно и меняет картинку. ref — объект { current }, который живёт между рендерами, но не вызывает рендер; после commit в нём лежит DOM-узел.

        Как сказатьuseRef даёт объект, который живёт между рендерами, но его изменение не вызывает рендер — в отличие от state. Туда кладу то, что нужно помнить, а не показывать: id таймера, прошлое значение, последний колбэк, и DOM-узел, который React записывает в current после commit. В JSX ref не читаю: React не узнает об изменении.

        04

        Как устроены свои хуки и откуда правила хуков?

        Кастомный хук — функция с хуками внутри: делит логику, но каждый компонент получает свои слоты. Правила хуков — следствие нумерации слотов по порядку вызова.

        Как сказатьКастомный хук — обычная функция, внутри которой вызываются хуки; имя с use нужно линтеру. Он делит логику, а не состояние: каждый компонент получает свои слоты в своей карточке. Правила хуков следуют из этого: слоты нумеруются по порядку вызова, поэтому никаких хуков в условиях, циклах и после return.

        Какой хук когда

        1. useState — значение, которое видно на экране; смена → рендер
        2. useRef — помнить между рендерами без рендера; ссылка на DOM-узел
        3. useEffect — синхронизация с внешним миром после кадра: запросы, подписки, таймеры — с cleanup
        4. useLayoutEffect — измерить и поправить DOM до кадра; редко, блокирует отрисовку
        5. useMemo / useCallback — стабильная ссылка и кеш вычислений — соседний таб
        6. useContext / useSyncExternalStore — читать из дерева или из внешнего стора по срезу
        7. useTransition / useDeferredValue — понизить приоритет тяжёлого обновления

        Рассказ на минуту — из пяти фраз

        Эффекты идут после commit: useLayoutEffect синхронно до кадра — для измерений, useEffect после кадра — для запросов, подписок и аналитики. Эффект замыкает значения своего рендера, поэтому с пустыми deps таймер видит старый state — лечу функциональным обновлением или честными deps, линтер это подсвечивает. Cleanup запускается перед следующим эффектом и при размонтировании: там снимаю подписки и помечаю устаревшие запросы, а сам запрос отменяю через AbortController. useRef хранит объект между рендерами без ререндера — id таймера, прошлое значение, DOM-узел после commit. Свои хуки делят логику, а не состояние, и подчиняются правилам хуков, потому что слоты нумеруются по порядку вызова.

        Техническая основа: react.dev — Synchronizing with Effects, useLayoutEffect, useRef и Reusing Logic with Custom Hooks.

        Паттерны компонентов и дизайн-система

        00

        Композиция или пропсы-флаги?

        Пропсы — для поведения. Содержимое — через children и слоты.

        01

        Что такое compound components?

        Части одного виджета с общим состоянием через контекст; разметка как в HTML.

        Как сказатьCompound components — части одного виджета с общим состоянием через контекст: Tabs держит active, Tab и Panel читают его через useContext, разметка собирается как HTML.

        Controlled или uncontrolled?

        Разница — где живёт значение: в DOM или у родителя.

        Как сказатьControlled — значение у родителя через value и onChange, uncontrolled — в DOM, читаю при submit. Владеет значением тот, кто на него реагирует.

        Логику делят хуками; поведение с доступностью берут из headless-библиотек.

        04

        Как устроен компонент дизайн-системы?

        Как сказатьКомпонент дизайн-системы управляется вариантами и токенами, тег меняет через as или asChild. Storybook — контракт: story — состояние, play проверяет поведение, Chromatic — вид.

        Какой паттерн когда

        1. children и слоты — содержимое от родителя
        2. compound components — части с общим состоянием: Tabs, Select
        3. controlled / uncontrolled — родитель реагирует / читать при submit
        4. хук / render prop / HOC — логика / доступ к разметке / легаси
        5. headless — поведение из библиотеки, разметка своя
        6. дизайн-система — варианты, токены, story как контракт

        Ответ за 20 секунд — три фразы

        Раздел 03.6 / React

        Состояние и данные

        Пять вопросов — пять коротких ответов. Сцена показывает, строка «Как сказать» — то, что говоришь.

        00

        Какие бывают состояния и где их хранить?

        Четыре вида: UI, общее клиентское, серверные данные, URL. У каждого своё место.

        Как сказатьЛокальное — useState рядом с компонентом, общее клиентское — контекст или стор, серверные данные — кеш через React Query, фильтры и страница — в URL.

        01

        Что делает React Query и зачем он?

        Кеш серверных данных по ключу: статусы, дедупликация, фоновое обновление, инвалидация.

        Как сказатьReact Query — кеш серверных данных по ключу: статусы из коробки, дедупликация одинаковых запросов, показ кеша с фоновым обновлением, инвалидация после мутаций через invalidateQueries.

        02

        Контекст или Zustand / Redux?

        Контекст будит всех подписчиков, стор с селекторами — только тех, чей срез изменился.

        Как сказатьКонтекст — для редких изменений и DI, стор с селекторами (внутри useSyncExternalStore) — для частых обновлений и многих потребителей. Zustand по умолчанию, Redux Toolkit при строгих требованиях.

        03

        Zustand, Redux Toolkit, RTK Query, MobX

        Три из четырёх — про клиентское состояние и отличаются ценой и строгостью. RTK Query стоит отдельно: это данные сервера, а не общий стор.

        Не общий стор, а данные сервера: кеш по ключу, статусы, дедупликация одинаковых запросов и инвалидация после мутации.

        Зависимости отслеживаются сами: селекторы писать не нужно. Компонент перерисуется, только если читал изменившееся поле.

        Как сказатьZustand — хук-стор без провайдера, подписка селектором, минимум кода: обычный выбор для клиентского состояния. Redux Toolkit даёт строгий поток через action и reducer и полную историю изменений, но стоит дороже по коду. RTK Query — это не стор, а слой серверных данных поверх Redux: кеш по ключу, статусы и инвалидация после мутации. MobX сам отслеживает зависимости, поэтому селекторы не нужны, но состояние меняется напрямую и это дальше от привычного React-подхода.

        04

        Почему нельзя дублировать state?

        Производное считают в рендере, тяжёлое — через useMemo; копия через useEffect даёт лишний рендер и рассинхрон.

        Как сказатьПроизводное считаю прямо в рендере, тяжёлое — через useMemo. State держу минимальным и нормализованным, без копий через useEffect.

        05

        Как показать ответ LLM по мере генерации?

        Как сказатьЧитаю ответ потоком через ReadableStream или SSE, коплю чанки и обновляю state раз в кадр, стоп — через AbortController, статусы idle, streaming, done, error.

        Где что хранить

        1. локальное UI — useState рядом с компонентом
        2. общее клиентское — контекст, если меняется редко; стор с селекторами, если часто
        3. серверные данные — React Query / SWR — кеш по ключу, не стор
        4. фильтры, страница, сортировка — в URL

        Раздел 04 / Архитектура

        Feature-Sliced Design

        FSD — это правила, куда класть код и кому кого можно импортировать. Уровень отвечает за роль кода, слайс — за кусок предметной области, импорт разрешён только вниз.

        00

        Уровень — что на нём лежит

        Шесть уровней сверху вниз. Чем ниже, тем меньше знаний о продукте и тем больше переиспользования.

        Как сказатьУровни идут сверху вниз: app — сборка приложения, pages — экран целиком, features — действие пользователя, entities — модель домена, shared — инфраструктура без бизнес-логики. Импортировать можно только вниз и нельзя соседа на своём уровне.

        01

        Какие проблемы решает

        Пять болей растущего фронтенда и ответ FSD на каждую.

        1. «Куда положить этот файл?» — спор на каждом ревью

          Есть правило по умолчанию: сначала кладём в pages, выносим ниже только когда код реально используется в двух местах.

        2. Всё импортирует всё, появляются циклы

          Импорт разрешён только вниз, соседей на своём уровне — нельзя. Цикл структурно невозможен, это проверяет линтер Steiger.

        3. Тронул одно — сломалось в трёх местах

          У слайса есть граница: наружу торчит только index.ts. Внутренности можно переписать, не трогая тех, кто им пользуется.

        4. Файлы types.ts и utils.ts на две тысячи строк

          Внутри слайса сегменты по назначению — ui, model, api, lib — а имена файлов по домену: product.ts, fetch-cart.ts.

        5. Новый человек не понимает, где что живёт

          Путь в импорте говорит и уровень, и смысл: features/add-to-cart — это действие, entities/product — модель домена.

        Где не надо усердствовать

        • Маленькому проекту хватает трёх уровней: app, pages, shared. Пустые папки «на будущее» заводить не нужно.
        • Слой widgets в v2.1 заводить не советуют: его границы путаются с features. Композиция экрана остаётся в pages.
        • Entities и features создаём только тогда, когда код уже используется повторно, а не когда кажется, что пригодится.

        Как сказатьFSD отвечает на два вопроса: куда положить код и кому кого можно импортировать. Он убирает споры на ревью, делает циклы невозможными и держит границу слайса — наружу торчит только публичный index.ts.

        02

        Один пример: кнопка «Добавить в корзину»

        Одна кнопка разложена по уровням: видно, кто кого импортирует и почему обратно нельзя.

        Как сказатьСтраница корзины берёт готовую кнопку из features, кнопка использует карточку товара из entities, карточка собрана из кнопки в shared. Обратно нельзя: entities ничего не знает про features. Пока действие живёт на одной странице, оно остаётся в pages — выношу его в features, только когда оно понадобилось на второй.

        Техническая основа: feature-sliced.design и Steiger — линтер FSD.

        Раздел 05.1 / TypeScript

        type и interface

        Два вопроса — два коротких ответа. Сцена показывает, строка «Как сказать» — то, что говоришь.

        00

        Что умеет только interface, а что — только type?

        interface: слияние объявлений и дополнение чужих типов. type: объединения, кортежи, примитивы и вычисляемые типы. Объекты, функции и расширение умеют оба.

        Как сказатьТолько interface умеет слияние объявлений, поэтому им дополняют типы библиотек. Только type умеет объединения, кортежи и вычисляемые типы: keyof, mapped, conditional. Объекты, функции и расширение умеют оба.

        01

        Какие проблемы решают interface и type?

        interface — контракты и расширяемые формы. type — состояния экрана как объединение и типы, выведенные из других типов.

        Как сказатьinterface решает контракты: класс обязан реализовать методы, формы собираются через extends. type решает состояния и производные типы: объединение по status исключает невозможные комбинации, Partial и keyof выводят тип из типа.

        Техническая основа: TypeScript Handbook — Differences Between Type Aliases and Interfaces, Declaration Merging.

        Раздел 05.2 / TypeScript

        Generics

        Два вопроса — два коротких ответа: зачем нужны generics и где им место.

        00

        Зачем нужны generics?

        Generic — это функция или тип с параметром типа: подставил number — получил number, подставил string — получил string. Без него пришлось бы писать any или копировать функцию под каждый тип.

        Как сказатьGeneric — параметр типа: компилятор выводит T из аргумента, и тип выхода связан с типом входа без any и без копий функции. Тот же механизм в useState, Promise и обёртках вроде ApiResponse.

        01

        extends, keyof и когда generic лишний

        extends ограничивает T, keyof с T[K] даёт безопасный доступ к полю, generic-компонент выводит T из items. Если типы входа и выхода не связаны, generic не нужен.

        Как сказатьextends ограничивает T, чтобы внутри был доступ к нужным полям, keyof с T[K] даёт безопасный доступ к свойству. Generic нужен, когда типы входа и выхода связаны; иначе хватит union, а параметр типа на один раз — лишний.

        Техническая основа: TypeScript Handbook — Generics, Indexed Access Types.

        Раздел 05.3 / TypeScript

        any, unknown, never

        Один вопрос — четыре шага: выключенная проверка, проверка перед использованием, «не бывает».

        00

        any, unknown, never

        any выключает проверку. unknown — проверь перед использованием. never — «не бывает»: исчерпывающий switch и несовместимые пересечения.

        Как сказатьany выключает проверку и заражает всё вокруг. unknown говорит «значение есть, тип неизвестен» — сначала сузить через typeof, instanceof или схему. never — тип, которого не бывает: им ловлю необработанный вариант union в default и вижу ошибку в пересечениях.

        Техническая основа: TypeScript Handbook — Everyday Types: any, Narrowing: the never type.

        Раздел 05.4 / TypeScript

        Сужение типов

        Один вопрос — четыре шага: дискриминант, typeof и instanceof, свой предикат.

        00

        Как сужается тип?

        Дискриминант kind, typeof, instanceof, in и свой предикат x is User — компилятор следит за ветками.

        Раздел 05.5 / TypeScript

        Utility types, as const, satisfies

        Пять вопросов — пять коротких ответов. Сцена показывает, строка «Как сказать» — то, что говоришь.

        00

        Объекты: Partial, Required, Readonly, Pick, Omit, Record

        Новый тип из существующего без копирования полей.

        Как сказатьPartial и Required переключают обязательность полей, Readonly запрещает запись, Pick и Omit берут или убирают поля, Record строит объект по ключам union. Всё это mapped types под капотом, и они комбинируются.

        01

        Объединения: Extract, Exclude, NonNullable

        Оставить, убрать или очистить варианты union.

        Как сказатьExtract оставляет варианты объединения, Exclude выбрасывает, NonNullable убирает null и undefined. Они идут по каждому варианту по очереди, поэтому Extract по форме выбирает нужный объект из объединения.

        02

        Функции и классы: Parameters, ReturnType, InstanceType

        Вытащить типы из функции или класса, не описывая их второй раз.

        Как сказатьParameters и ReturnType достают типы аргументов и результата из функции, ConstructorParameters и InstanceType — то же для классов, а ThisParameterType, OmitThisParameter и ThisType работают с this. Так обёртки, моки и фабрики не дублируют типы.

        03

        Awaited, NoInfer и строковые: Uppercase, Capitalize

        Тип после await, контроль вывода T и регистр литеральных строк.

        Как сказатьAwaited даёт тип после await и разворачивает вложенные Promise, NoInfer запрещает выводить T из конкретного аргумента. Uppercase, Lowercase, Capitalize и Uncapitalize меняют регистр литеральных строк, обычно внутри шаблонных строковых типов.

        04

        as const и satisfies

        Точные типы из данных и проверка формы без расширения.

        Как сказатьas const превращает данные в литеральные readonly-типы, а typeof с [number] достаёт из массива union значений. satisfies проверяет, что значение подходит под тип, но оставляет его точным, в отличие от аннотации, которая расширяет.

        Техническая основа: TypeScript Handbook — Utility Types, TypeScript 4.9 — satisfies.
