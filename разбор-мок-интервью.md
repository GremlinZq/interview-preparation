# Мок-интервью 02.09.2026 — что не дожал

## TypeScript

**1. `type` vs `interface` — назвал только «наследование», и неверно.**
Полный каркас ответа:

| | `interface` | `type` |
|---|---|---|
| Declaration merging / module augmentation | ✅ только он | ❌ Duplicate identifier |
| Union (`A \| B`) | ❌ | ✅ |
| Примитивы, кортежи, алиасы | ❌ | ✅ |
| Conditional / mapped / template literal | ❌ | ✅ |
| Расширение | `extends` — ошибка при конфликте | `&` — молча `never` |
| Компилятор на больших графах | быстрее, кэшируется | цепочки `&` дороже |

Главный козырь `interface` — declaration merging: расширить тип чужой библиотеки иначе нельзя.

**2. Конфликт при расширении — ответил наоборот.**
`&` — это НЕ перезапись, это «и то, и другое». `string & number` = `never`.
```ts
interface B extends A { id: number }   // ❌ ошибка сразу, на объявлении
type B2 = A & { id: number }           // ✅ молчит, id становится never
const x: B2 = { id: 1 }                // ❌ ошибка вылезает здесь, в другом файле
```
Аргумент для интервью: публичные контракты — на `interface`, ошибка приходит рано и в точке объявления.

**3. Exhaustiveness check — не назвал, даже с подсказкой. ⚠️ Очень частый вопрос.**
```ts
default: {
  const _exhaustive: never = node
  throw new Error(`Unknown node: ${JSON.stringify(_exhaustive)}`)
}
```
Все ветки обработаны → в `default` тип сужается до `never`. Добавили вариант в union → тип уже не `never` → сборка падает ровно здесь.

Что ломает защиту: дискриминант типа `string` вместо литерала; `default: return null`; enum вместо union строковых литералов (рантайм-объект, хуже tree-shaking, конфликт `const enum` с `isolatedModules`).

Декларативная альтернатива: `Record<Node['type'], Renderer>` — пропущенный ключ даёт ошибку компиляции.

**4. Два слоя валидации — смешал их.**

| | Ответ LLM невалиден | Пользователь ввёл ерунду |
|---|---|---|
| Чья ошибка | системы | пользователя |
| Кому показывать | никому: лог + телеметрия | ему, под полем |
| На экране | плейсхолдер + «Сгенерировать заново» | `errorMessage` у инпута |
| Восстановление | retry с фидбеком модели | юзер исправит сам |

Production-ready версия: `safeParse` вместо `parse`; валидация по-нодно (битая нода → плейсхолдер, остальные рендерятся); error boundary на каждую ноду; self-healing retry — `error.issues` обратно в модель; structured outputs на входе; доля невалидных схем как метрика качества фичи.

## JavaScript

**6. Stale closure — не дал конкретный ответ.** Интервал печатает `0` вечно, на экране при этом `5`.
Формулировка наизусть: «каждый рендер — отдельный снимок; `count` не переменная, а константа внутри конкретного рендера». Эффект с `[]` замкнулся на окружении первого рендера.
Три починки: честные deps (`[count]`, но таймер сбрасывается) / функциональный апдейт `setCount(c => c + 1)` / latest ref (`countRef.current`, таймер не сбрасывается).

**7. `this` в `setTimeout` — ответ хороший, три уточнения.**
- `call`/`apply` вызывают немедленно → для `setTimeout` не годятся (ты это сам оговорил, плюс).
- Не назвал стрелочную обёртку: `setTimeout(() => user.getName(), 1000)`.
- `setTimeout(user.getName(), 1000)` — вызов прямо сейчас, в таймер уходит строка. Классика ревью.
- Не `undefined`: в браузере `this === window`, `window.name` → `''` (пустая строка). `undefined` только в Node (объект `Timeout`).
- Формулировка: «`this` определяется способом вызова, а не местом объявления».

**8. `__proto__` vs `prototype` — путаница. ⚠️ База, спрашивают почти всегда.**
- `prototype` — свойство **функции-конструктора**, у обычных объектов его нет. Это объект, который станет прототипом будущих экземпляров.
- `__proto__` — свойство **любого объекта**, ссылка на его реальный прототип. Современный доступ: `Object.getPrototypeOf` / `Object.setPrototypeOf`.
- `instance.__proto__ === Foo.prototype` → **true, один объект в памяти, не копия**.
- ❌ Твоя ошибка: `instance.__proto__.bar = 1` меняет `Foo.prototype` и мгновенно всех экземпляров, включая уже созданные.

**Что делает `new Foo()` — четыре шага, спрашивают дословно:**
1. Создаётся новый пустой объект.
2. Его `[[Prototype]]` ставится на `Foo.prototype`.
3. Функция вызывается с `this` = этот объект.
4. Вернула объект → возвращается он; иначе возвращается `this`.

**9. Методы класса vs поля-стрелки — ошибся в первом.**
```js
a.bar === b.bar   // true  — bar лежит в Foo.prototype, один объект на всех
a.baz === b.baz   // false — поле-стрелка создаётся заново в конструкторе
```
Следствия: память (1000 экземпляров → 1000 функций); стрелочное поле автопривязано к экземпляру (поэтому так делали вместо `bind` в классовых компонентах); минус — его нельзя переопределить в наследнике и нельзя подменить через прототип в тестах.
Верно отметил: у стрелочной функции нет `.prototype`, поэтому её нельзя вызвать через `new`.

**10. `race` и `any` — поменял местами.**

| | Когда завершается | Если все упали |
|---|---|---|
| `all` | все успешно; первый reject валит всё | reject первой ошибкой |
| `allSettled` | всегда, массив `{status, value/reason}` | не падает |
| `race` | первый **заселившийся** — успех или ошибка | — |
| `any` | первый **успешный**, отказы игнорирует | `AggregateError` |

Мнемоника: **`any` — любой успех, `race` — любой финиш.**

**11. Отмена запросов — неверно. ⚠️** Резолвить чужой промис нельзя, и это не отменяет запрос: трафик качается, сервер отвечает, ты просто игнорируешь результат.
```js
useEffect(() => {
  const ac = new AbortController()
  fetch(url, { signal: ac.signal })
    .catch(e => { if (e.name !== 'AbortError') report(e) })
  return () => ac.abort()
}, [url])
```
Разведи: **«проигнорировать результат» ≠ «отменить запрос»**. В React Query `signal` приходит прямо в `queryFn`. В твоём проекте это же самое — кнопка «Стоп» во время стриминга ответа LLM.

## Сети и деплой

**12. Кэширование статики — `index.html` верно, хэшированный чанк наоборот. ⚠️ Важно для пункта «CI/CD, деплой фронтенда» в вакансии.**

Ключевая идея, которую ты не увидел: **имя файла — это хэш его содержимого.** Изменится содержимое → изменится имя. Значит файл по этому URL не может измениться никогда. Он неизменяем по определению.

| Файл | Заголовок | Почему |
|---|---|---|
| `index.html` | `no-cache` (или `max-age=0, must-revalidate`) | точка входа, знает имена текущих чанков, должна ревалидироваться всегда |
| `main-a3f9c2.js`, css, шрифты с хэшем | `public, max-age=31536000, immutable` | контент-хэш в имени → URL неизменяем |
| favicon, robots, manifest (без хэша) | короткий `max-age` + ревалидация | меняются редко, но имя стабильное |
| API-ответы | `no-store` для приватных, иначе `private` + ETag | |

`immutable` важен отдельно: без него браузер при F5 всё равно шлёт условный запрос и получает 304 — лишний round-trip на каждый чанк. С `immutable` не шлёт вообще.

❌ `no-store` на бандл — худшее решение: весь JS качается заново при каждом заходе.

Правило: **versionируется через имя → кэшируем навсегда. Не versionируется, но должно быть свежим → не кэшируем.**

**13. Chunk load error после релиза — не знал (признался честно, это правильно).**

**Что происходит:** `import()` возвращает отклонённый промис — `Failed to fetch dynamically imported module`. Важно: **Suspense такие ошибки не ловит**, ловит только Error Boundary. Нет boundary → падает всё дерево, белый экран.

**Четыре уровня решения, от дешёвого к правильному:**

1. **Не удалять старые чанки при деплое.** Держать 2–3 последние версии, чистить по TTL. Снимает 90% проблемы. В CI это `cp` поверх вместо `sync --delete`.
2. **Порядок деплоя:** сначала ассеты, потом `index.html`. Иначе окно, где свежий html ссылается на ещё не залитые чанки.
3. **Ретрай + перезагрузка на клиенте:**
```js
const retryImport = (fn, retries = 2) =>
  fn().catch(err => {
    if (retries > 0)
      return new Promise(r => setTimeout(r, 500)).then(() => retryImport(fn, retries - 1))
    if (!sessionStorage.getItem('chunk-reloaded')) {
      sessionStorage.setItem('chunk-reloaded', '1')   // защита от цикла перезагрузок
      location.reload()                               // подтянет свежий index.html
    }
    throw err
  })
const Page = lazy(() => retryImport(() => import('./Page')))
```
В Vite есть готовое событие: `window.addEventListener('vite:preloadError', () => location.reload())`.
4. **Проактивно:** билд кладёт `version.json`; приложение при возврате фокуса на вкладку сравнивает версии и показывает ненавязчивый тост «доступна новая версия». Твоя идея, но с механизмом и без алерта посреди заполнения формы.

Плюс **Error Boundary вокруг lazy-роутов обязателен**.

**15. Build once, deploy anywhere — ответил как мидл. ⚠️ Ключевая развилка мидл/сеньор.**

Ты: «под каждый стенд своя ветка и своя сборка, адрес бэкенда зашивается на этапе сборки, откат = ревертнуть ветку и пересобрать».

Почему это неправильно: если собираешь отдельный бандл под каждый стенд, то **артефакт, протестированный на stage — не тот, что поехал в prod**. Другая сборка, другие хэши. Промоушен превращается в пересборку = время + новый риск.

Правильно: **один артефакт (docker image / папка статики) проходит dev → stage → prod без пересборки.** Это `artifact promotion`. Конфиг — в рантайме.

Три способа рантайм-конфига во фронте:
1. `/config.json` рядом с ассетами, фетчится до старта приложения, не кэшируется.
2. Nginx подставляет env в `index.html` при старте контейнера (`envsubst` в entrypoint) → `window.__ENV__`. Самый частый приём для докеризированного фронта.
3. Вообще не хранить адрес: ходить на относительный `/api`, роутит reverse proxy на каждом стенде.

**Откат за две минуты.** Ревертнуть ветку и пересобрать — это НЕ откат, это 15 минут и шанс, что билд упадёт.
- **Атомарный деплой:** каждая версия в своей папке `/releases/<sha>/`, указатель `current` — симлинк. Откат = переключить указатель, секунды.
- **Docker:** задеплоить предыдущий тег образа.
- **Feature flag** — самый мягкий откат: выключить фичу вообще без релиза.

**16. Feature flags и A/B — блок пропущен по твоей просьбе.** Остаётся дырой: в вакансии это два отдельных пункта обязанностей. ## React

**17. Фазы рендера — ⚠️ большая дыра, спрашивают почти всегда.**

Правильный ответ — три фазы:

**1. Вызов `setState`.** React не обновляет стейт немедленно: кладёт обновление в очередь на конкретном Fiber-узле и планирует работу через Scheduler с приоритетом (lane). Несколько `setState` в одном событии батчатся в один рендер (в React 18 — автоматически везде, включая промисы и таймауты; в 17 — только внутри React-событий).

**2. Render phase.** React вызывает функцию компонента, строит новое дерево Fiber, сравнивает со старым (reconciliation).
- **Может быть прервана, отброшена и запущена заново с нуля.**
- Поэтому обязана быть **чистой**: никаких мутаций, запросов, `document.title = ...` в теле компонента.
- Поэтому StrictMode в dev вызывает компонент дважды — ловит нечистоту.

**3. Commit phase.** React применяет изменения к настоящему DOM.
- **Синхронна и непрерываема** — иначе пользователь увидел бы наполовину обновлённый UI.
- Порядок внутри: мутация DOM → `useLayoutEffect` (синхронно, **до paint** — здесь измеряют и правят, чтобы не было мигания) → браузер рисует → `useEffect` (**после paint**, асинхронно).

❌ Твоя ошибка: сказал, что `useEffect` отрабатывает **до** отрисовки. Наоборот — после. До отрисовки только `useLayoutEffect`.

**Формулировка наизусть: render — чистый и прерываемый, commit — грязный и непрерываемый.**
